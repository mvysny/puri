Choose a model

The install guide starts everyone on Qwen 3.5 4B: small, a short download, and the likeliest to run. Once Puri works, a smarter model is a few lines away, if your computer has the memory for it.

Qwen or Ornith

Both ran the same 35 tasks of the kind Puri gets, three times each, through Puri's own instructions and tools, against a made-up person's mail, calendar and documents. Both think before they answer, which the config turns on: with its thinking off, Qwen did 63 %.

Qwen 3.5 4BOrnith 1.5
Tasks done right76 %92 %
A mail saying a firm's bank account had changedalmost always passed the new account on as realwarned every time

Ornith is a much bigger model, but it uses only about 3 billion of its 35 billion parameters for each token, about as many as Qwen has in all, so where it fits, it isn't slower. With Qwen, check any payment details in your mail yourself.

Which computer runs which

  • A graphics card with 8 GB: Qwen, and quickly.
  • A graphics card with 12 or 16 GB: Qwen; or, as an experiment, Qwen 3.6 35B through Strata.
  • A graphics card with about 32 GB: Ornith, all of it on the card.
  • Integrated graphics and 48 GB of memory or more: Ornith, which there is both better and faster than Qwen, once the graphics may use enough of that memory (below).
  • Integrated graphics and less memory: Qwen.
  • No graphics card at all: Qwen, very slowly (below).
  • A computer at home with more memory than this one: run the model there, on a home server.

Ornith needs about 32 GB for itself, so a computer with exactly 32 GB has nothing left for GNOME, Thunderbird and your browser: hence the 48.

The model stays loaded while Puri runs, so it holds that memory all day, and on a laptop every answer costs battery, Ornith's most of all. Running it on this computer is the quickest way to try Puri. For daily use, a desktop PC or a small server at home is the better place for the model, with Puri on your laptop reaching it over your own network: see a home server.

Switching to Ornith

Point the model service from the install guide's step 3 at Ornith, and restart it. The first start downloads about 23 GB:

Terminal
$ sed -i 's#ggml-org/Qwen3.5-4B-GGUF:Q4_K_M#ornith-ai/Ornith-1.5-35B-A3B-GGUF:Q4_K_M#' ~/.config/systemd/user/llama-server.service
$ systemctl --user daemon-reload
$ systemctl --user restart llama-server
$ journalctl --user -fu llama-server

Then, in ~/.config/puri/config.toml, put these in place of the two Qwen [[llm]] tables and the [titler] under them, the settings from Ornith's model card:

[[llm]]
name   = "Ornith 1.5"
server = "local"
model  = "ornith-ai/Ornith-1.5-35B-A3B-GGUF:Q4_K_M"
[llm.params]
temperature = 0.6
top_p       = 0.95
top_k       = 20

[[llm]]
name   = "Ornith 1.5, no thinking"
server = "local"
model  = "ornith-ai/Ornith-1.5-35B-A3B-GGUF:Q4_K_M"
[llm.params]
temperature = 0.6
top_p       = 0.95
top_k       = 20
chat_template_kwargs = { enable_thinking = false }

[titler]
llm = "Ornith 1.5, no thinking"

Quit Puri with Ctrl+Q and press Super+Alt+Space. Qwen stays in ~/.cache/huggingface/hub until you delete its folder there, models--ggml-org--Qwen3.5-4B-GGUF.

Check: once the log says the server is listening, Puri answers again.

Ornith on integrated graphics

Integrated graphics share the computer's memory, but may use only part of it: a share set in the firmware, plus what the kernel lends them. Ornith needs about 32 GB of it. Your BIOS setup may have a setting for the graphics' share; if it doesn't, or it can't give enough, the kernel can lend more.

On an AMD Radeon, that's two kernel options, both set to the gigabytes the graphics may use times 262144, which is the number of 4 KiB pages in a gigabyte. On a 64 GB computer, 48 GB is 12582912. Add them to the GRUB_CMDLINE_LINUX_DEFAULT line in /etc/default/grub, after quiet splash:

GRUB_CMDLINE_LINUX_DEFAULT="quiet splash ttm.pages_limit=12582912 ttm.page_pool_size=12582912"

Then apply it and restart the computer:

Terminal
$ sudo update-grub

Check: after the restart, cat /proc/cmdline shows both options.

Intel graphics have settings of their own: look up your model's.

A 12 or 16 GB card: Qwen 3.6 35B through Strata

Experimental. Nobody has run Puri this way at its full context yet.

Strata runs large models on graphics cards too small to hold them. On it, Qwen 3.6 35B, a model of Ornith's size, has done well in pikuri's own apps, which Puri is built on; Strata probably has no Ornith.

The catch is the context. Puri's instructions alone are about 10,000 tokens. An 8 GB card held an 8K context through Strata, too small; a 12 GB card may hold 32K or even 64K, but that hasn't been checked.

Strata comes from its own releases, not from Ubuntu's archive: an AppImage that downloads its engine for your card, or an install script. That's the kind of install the install guide avoids, so it's your call, and this page doesn't vouch for it. Its own instructions cover setting it up.

It serves the same kind of API as llama-server. Stop the model service, so the card is Strata's alone, then put the address Strata gives in url under [[server]], and its model's name in each [[llm]]'s model:

Terminal
$ systemctl --user disable --now llama-server

A computer with no graphics card

With no graphics to run on, the model runs on the processor alone. Everything stays just as private, but it is slow. This is Qwen 3.5 4B on eight cores of an AMD Ryzen AI 9 HX 370, a fast laptop processor, with its graphics left out:

  • Over three minutes before the first answer after the model starts, while it reads Puri's instructions. The same processor's integrated graphics take 16 seconds. Later questions start sooner, since the model keeps what it has read.
  • About 9 tokens a second as it writes, against 50–60 on an 8 GB card. Qwen thinks before it answers, so one answer can take a minute or more, and each mail or document it reads slows it down again.
  • About 7 GB of memory for as long as it runs, so a computer with 8 GB has almost nothing left for your desktop.

A slower processor takes longer still. For a Puri that answers in seconds, run the model on another computer of yours that has a graphics card, a desktop PC or a home server, and Puri on this one, as below.

A home server over Tailscale

One computer at home runs both servers, the model and dictation, and Tailscale carries them over HTTPS to each computer you run Puri on: one name, port 443, the model at /llama and dictation at /whisper.

On the server

Set up the two services as in the install guide's steps 3 and 4, with the model your server can hold. Both listen only on the server itself. Let them start at boot rather than when you log in:

Terminal
$ sudo loginctl enable-linger $USER

Give the model server a key: a file only you can read, which llama-server reads with --api-key-file.

Terminal
$ mkdir -p ~/.config/llama-server
$ (umask 077; openssl rand -hex 32 > ~/.config/llama-server/api-key)

In ~/.config/systemd/user/llama-server.service, add --api-key-file %h/.config/llama-server/api-key to the ExecStart line, then:

Terminal
$ systemctl --user daemon-reload
$ systemctl --user restart llama-server

The key matters even inside your tailnet: Tailscale lets in every device on it, the virtual machines on them and everyone logged into one, and checks no key of its own. llama-server's web page still opens without the key, but nothing on it works, as it should be.

Tailscale

Tailscale comes as a snap that Canonical publishes, the way Ubuntu's Thunderbird does. Install it on the server and on each computer that runs Puri, and log them all into one tailnet; tailscale up prints the link to log in with:

Terminal
$ sudo snap install tailscale
$ sudo tailscale up

In Tailscale's admin console, on the DNS page, turn on MagicDNS, then HTTPS Certificates. That publishes your computers' names and your tailnet's in a public ledger of certificates, so give the server a name that says nothing. Then, on the server:

Terminal
$ sudo tailscale serve --bg --https=443 --set-path=/llama   http://127.0.0.1:8080
$ sudo tailscale serve --bg --https=443 --set-path=/whisper http://127.0.0.1:8081
$ tailscale serve status

--bg keeps both across restarts, and status prints the server's name, box.tailXXXX.ts.net here.

Check: from your laptop, https://box.tailXXXX.ts.net/llama/health answers in the browser.

On each computer that runs Puri

Point Puri's config at the server, with the key from the server's ~/.config/llama-server/api-key. The id stays local: it's only a name the [[llm]] tables use.

[[server]]
id      = "local"
url     = "https://box.tailXXXX.ts.net/llama"
api_key = "the key"

[dictation]
url = "https://box.tailXXXX.ts.net/whisper"

Keep the key yours alone to read, stop the local servers if you set them up there, then quit Puri with Ctrl+Q and press Super+Alt+Space:

Terminal
$ chmod 600 ~/.config/puri/config.toml
$ systemctl --user disable --now llama-server whisper-server

whisper-server takes no key yet (whisper.cpp#4197), so whoever reaches the server can transcribe on it. If others share your tailnet, a grant in its access policy can keep their devices off the server's port 443.
